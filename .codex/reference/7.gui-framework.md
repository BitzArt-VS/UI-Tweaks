# GUI framework

Read this reference when changing custom framework dialogs, component declarations,
layout, rendering, tooltips, overlays, focus, input routing, resizing, or the dialog
host.

## Boundary and entry points

The custom Cairo-backed framework is under
[`Gui/Framework/`](../../src/UI-Tweaks/Gui/Framework/). Its production consumer is
[`ModConfigDialog`](../../src/UI-Tweaks/Gui/Dialogs/ModConfigDialog.cs), which derives
from the framework's `GuiDialog` and declares a keyed C# component tree.

[`QuickSearchGuiDialog`](../../src/UI-Tweaks/Gui/Dialogs/QuickSearchGuiDialog.cs) is
outside this framework. It derives from `VanillaGuiDialog` and uses Vintage Story's
`GuiComposer`; do not apply custom-tree assumptions to it.

## Logical map

```text
GuiDialogHost
  -> one DialogRenderer per open dialog type
     -> GuiElementAdapter integrates with Vintage Story dialog ordering and events
     -> GuiTreeBuilder owns and reconciles mounted component instances
     -> Cairo main surface
     -> overlay floating layer
     -> tooltip floating layer
     -> GuiInputRouter dispatches recorded regions and focus-based input
```

- [`GuiDialogHostInstance`](../../src/UI-Tweaks/Gui/Framework/Public/Services/GuiDialogHostInstance.cs)
  keeps at most one renderer for each dialog type. Opening an existing dialog applies
  configuration and reconciles it in place; closing disposes the renderer and tree.
- [`DialogRenderer`](../../src/UI-Tweaks/Gui/Framework/Internal/Renderers/DialogRenderer.cs)
  requires a fixed-width, fixed-height root dialog. It publishes `TooltipHost`,
  `FocusManager`, `OverlayHost`, and `GuiCursorHost` as root cascading values.
- Each `GuiSurfaceRenderer` publishes its own `ClippingContext` as the nearest cascading
  value, so the main dialog, overlay, and tooltip surfaces keep independent clipping
  state and coordinate spaces.
- [`GuiElementAdapter`](../../src/UI-Tweaks/Gui/Framework/Internal/Adapters/GuiElementAdapter.cs)
  is the bridge into Vintage Story's dialog render and input lifecycle.

## Declaration and reconciliation

`BuildComponentTree` declares a complete current subtree; it does not construct or
own child instances. [`GuiTreeBuilder`](../../src/UI-Tweaks/Gui/Framework/Internal/Services/GuiTreeBuilder.cs)
owns instances and reconciles declarations by `(concrete type, integer key)`.
That identity must be unique among siblings.

For a mounted slot on each pass, the builder:

1. resets per-pass configuration, callbacks, and component layout parameters;
2. runs the node's `ConfigureSlot` defaults and own-slot callbacks;
3. applies external `Configure` and `ConfigureLayout` actions;
4. combines own callbacks before external callbacks;
5. runs `OnInitialized` only for a new instance and `OnParametersSet` every pass;
6. reconciles the declared child subtree and disposes stale subtrees children-first.

Re-register all declarative values and callbacks on every pass. A missing declaration
means removal, not “keep the old value.” Cascading values are logical scopes and do
not create slots or affect layout.

## Nodes and layout

- `IGuiNode` participates in the tree but not necessarily in layout. A pure
  [`GuiNode`](../../src/UI-Tweaks/Gui/Framework/Public/Components/Base/GuiNode.cs) is
  layout-transparent; its arranged descendants determine its visual/input extent.
- `IGuiComponent` adds layout parameters and `Arrange()`. Mounted component results
  are cached as resolved absolute bounds in `GuiComponentSlot.Bounds`; transient
  parent-facing results may instead have relative positions as described below.
- [`GuiPoint`](../../src/UI-Tweaks/Gui/Framework/Public/Common/GuiPoint.cs) distinguishes
  resolved coordinates (`IsAbsolute = true`) from relative displacements (the default).
  Point-to-point addition and subtraction require exactly one absolute operand and one
  relative operand and return an absolute point. Adding or subtracting `GuiThickness`
  requires an absolute point and preserves that absolute result. Producers of render,
  input, popup, resize, and root-surface coordinates must therefore mark their points
  absolute explicitly; alignment offsets, flow advancement, and resize deltas remain
  relative.
- `GuiComponentLayoutParameters.Position` is the sole component-placement declaration.
  `null` preserves the aligned position and participates in sibling flow. A relative
  point offsets the aligned position and also participates in flow. An absolute point is
  the component's resolved border position, replaces alignment-based placement, and is
  excluded from sibling flow and parent fit-content measurement. Components that own
  independently positioned children assign those absolute points during their own
  `Arrange()` after their bounds are known.
- `HorizontalAlignment` and `VerticalAlignment` both use
  `GuiAlignment.Start`, `Center`, or `End`. Alignment offsets a resolved component size
  within the corresponding finite available dimension. `Start` needs no finite length;
  `Center` and `End` leave the position unresolved when either relevant length is
  unresolved. A dimension that fills all available space has no visible alignment
  displacement.
- `GuiComponentLayoutParameters.Width` and `Height` are optional explicit rules. A
  `null` dimension fits measured descendant margin bounds plus the component's padding;
  final empty content therefore resolves to padding alone before minimum and maximum
  constraints are applied. Relative descendant X/Y offsets contribute to measured
  width/height extent, so centered or end-aligned content does not lose its leading gap.
- Arrangement carries provisional bounds downward before carrying final descendant
  margin bounds upward. A fit-content dimension initially uses available space as its
  measurement envelope; the final overload treats a `null` descendant result as measured
  empty content rather than unmeasured content.
- Parent-to-child arrangement carries two envelopes: the remaining sibling-flow bounds
  and the layout parent's complete content bounds. Transparent `GuiNode` slots forward
  both. A component is first arranged in the remaining bounds. A returned absolute
  result causes `GuiComponentSlot` to arrange it again against the complete bounds when
  those envelopes differ, ensuring fill and fractional rules use the full parent.
- Flow-participating components return bounds whose position is relative to the bounds
  supplied by the parent. The parent resolves that result against the exact assigned
  origin before wrapping, union, and flow advancement; the component slot itself retains
  resolved absolute bounds for descendants, rendering, and input. Flow advances through
  the child's actual outer edge, including any alignment gap. Combined descendant extent
  is converted back to a relative result before travelling farther upward.
- Absolute component results are already resolved. Parents do not translate them, advance
  flow for them, or include them in returned descendant extent. An absolute-only subtree
  behind transparent nodes therefore returns no relative flow extent while its component
  slots retain their absolute caches. The public root `GuiSlot.Arrange()` boundary
  resolves any final relative result before returning it to an external caller.
- When a component's final bounds differ from its provisional bounds, it arranges its
  descendants again with the final bounds as the next provisional candidate. The original
  parent-provided availability remains the basis for fractional explicit, minimum, and
  maximum rules throughout these passes. Stabilization is recursive and limited to ten
  passes per component; an `InvalidOperationException` identifies a component whose
  bounds still differ after the limit, exposing circular fit-content/fractional layouts.
- `GuiLengthRule.Resolve()` returns a concrete logical-pixel length for fixed rules
  without requiring available space. Fractional rules return `null` when no available
  length exists. `GuiLengthRule.Fill` and `"100%"` both represent `Fraction(1)` and
  consume all available length.
- Static `GuiLengthRule.Resolve(...)` resolves one component dimension from optional
  explicit, minimum, and maximum rules. `available` is the parent-provided basis for
  fractional rules. The four-parameter overload also uses it as the provisional
  candidate; the five-parameter overload accepts a separate provisional or content
  candidate.
  The result is `null` when the dimension remains unlimited.
- A dialog is a component with screen-centred offsets and an attached dialog runtime.
  `IGuiResizable` is an independent capability discovered from arranged nodes.
- Components register resolved descendant clips through the cascading `ClippingContext`
  during arrangement. The surface resets registrations at the start of each layout walk
  and retains them for render-only walks. Nested clips intersect; a clip constrains
  descendant drawing and pointer/resize hit testing without constraining the owning
  node's drawing, input region, or overlay.
- `GuiContainer` owns all scrolling behavior. Its arrangement measures content, filters
  fit-content axes, reserves scrollbar gutters, clamps offsets, registers its viewport
  clip, and rearranges descendants against translated content bounds. It also owns wheel
  and scrollbar-drag input plus inset and scrollbar drawing. Tree-builder, renderer, and
  slot internals contain no scrolling-specific behavior.

## Invalidation and frame work

| Request | Intended use | Work scheduled |
| --- | --- | --- |
| `RequestReconcile()` | Declarations or configured values may change | Rebuild affected subtree, then layout and render. |
| `RequestLayout()` | Bounds, clipping, scrolling, or input regions may change | Arrange roots, rebuild regions, and render. |
| `RequestRender()` | Only visual state changed | Paint from cached bounds without rebuilding regions. |

`DialogRenderer` advances the focused node, drains scoped rebuilds, checks GUI scale
and dialog size, performs the strongest pending invalidation, blits the main texture,
then renders overlay and tooltip layers. Cairo component coordinates are logical
pixels; the surface context applies `RuntimeEnv.GUIScale`.

## Input model

- Mouse and resize routing use regions recorded from positioned layout results.
  Reverse-order hit testing gives later-rendered regions priority, and mouse-down
  capture keeps release behavior tied to the pressed region. Descendant clips are stored
  separately from original region bounds so clipping does not alter resize geometry.
- Mouse-wheel handlers use the same declarative slot registration and reverse-order
  routing as other mouse handlers, allowing nested scrolling components to win over
  scrolling ancestors.
- Keyboard routing is focus-based. Root-dialog handlers run before handlers for the
  node tracked by `FocusManager`.
- Mouse-down without a focus request blurs the focused node. Escape first blurs an
  active node; a later Escape with no focused node requests dialog close.
- Tooltips are visual-only floating content. Overlay layers may contribute interactive
  regions outside the main dialog surface.
