# GUI framework

Read this reference when changing custom framework dialogs, component declarations,
layout, rendering, tooltips, overlays, focus, input routing, resizing, or the dialog
host.

## Boundary and entry points

The custom Cairo-backed framework is under
[`Gui/Framework/`](../../src/UI-Tweaks/Gui/Framework/). Its production consumer is
[`ModConfigDialog`](../../src/UI-Tweaks/Gui/Dialogs/ModConfigDialog.cs), which derives
from the framework's `GuiDialog` and declares a keyed C# component tree.

[`QuickSearchGuiDialog`](../../src/UI-Tweaks/Gui/Dialogs/QuickSearchGuiDialog.cs) is
outside this framework. It derives from `VanillaGuiDialog` and uses Vintage Story's
`GuiComposer`; do not apply custom-tree assumptions to it.

## Logical map

```text
GuiDialogHost
  -> one DialogRenderer per open dialog type
     -> GuiElementAdapter integrates with Vintage Story dialog ordering and events
     -> GuiTreeBuilder owns and reconciles mounted component instances
     -> Cairo main surface
     -> overlay floating layer
     -> tooltip floating layer
     -> GuiInputRouter dispatches recorded regions and focus-based input
```

- [`GuiDialogHostInstance`](../../src/UI-Tweaks/Gui/Framework/Public/Services/GuiDialogHostInstance.cs)
  keeps at most one renderer for each dialog type. Opening an existing dialog applies
  configuration and reconciles it in place; closing disposes the renderer and tree.
- [`DialogRenderer`](../../src/UI-Tweaks/Gui/Framework/Internal/Renderers/DialogRenderer.cs)
  requires a fixed-width, fixed-height root dialog. It publishes `TooltipHost`,
  `FocusManager`, `OverlayHost`, and `GuiCursorHost` as root cascading values.
- [`GuiElementAdapter`](../../src/UI-Tweaks/Gui/Framework/Internal/Adapters/GuiElementAdapter.cs)
  is the bridge into Vintage Story's dialog render and input lifecycle.

## Declaration and reconciliation

`BuildComponentTree` declares a complete current subtree; it does not construct or
own child instances. [`GuiTreeBuilder`](../../src/UI-Tweaks/Gui/Framework/Internal/Services/GuiTreeBuilder.cs)
owns instances and reconciles declarations by `(concrete type, integer key)`.
That identity must be unique among siblings.

For a mounted slot on each pass, the builder:

1. resets per-pass configuration, callbacks, and component layout parameters;
2. runs the node's `ConfigureSlot` defaults and own-slot callbacks;
3. applies external `Configure` and `ConfigureLayout` actions;
4. combines own callbacks before external callbacks;
5. runs `OnInitialized` only for a new instance and `OnParametersSet` every pass;
6. reconciles the declared child subtree and disposes stale subtrees children-first.

Re-register all declarative values and callbacks on every pass. A missing declaration
means removal, not “keep the old value.” Cascading values are logical scopes and do
not create slots or affect layout.

## Nodes, layout, and current constraint

- `IGuiNode` participates in the tree but not necessarily in layout. A pure
  [`GuiNode`](../../src/UI-Tweaks/Gui/Framework/Public/Components/Base/GuiNode.cs) is
  layout-transparent; its arranged descendants determine its visual/input extent.
- `IGuiComponent` adds layout parameters and `Arrange()`. Mounted component results
  are cached in `GuiComponentSlot.Bounds`.
- `GuiLengthRule.Resolve()` returns a concrete logical-pixel length for fixed rules
  without requiring available space. Fractional rules return `null` when no available
  length exists.
- Static `GuiLengthRule.Resolve(...)` resolves one component dimension from optional
  explicit, minimum, and maximum rules. `available` is the parent-provided basis for
  fractional rules. The four-parameter overload also uses it as the provisional
  candidate; the five-parameter overload accepts a separate content or fill candidate.
  The result is `null` when the dimension remains unlimited.
- A dialog is a component with screen-centred offsets and an attached dialog runtime.
  `IGuiResizable` is an independent capability discovered from arranged nodes.

**Current implementation constraint:** the only `GuiComponent.Arrange()` implementation
in the current tree publishes provisional bounds and arranges its children, then calls
a final-resolution method that throws `NotImplementedException`; no component overrides
`Arrange()`. `GuiTreeBuilder.ArrangeRoot()` invokes that path before a layout render,
so component-owned arrangement remains an unfinished transition.

## Invalidation and frame work

| Request | Intended use | Work scheduled |
| --- | --- | --- |
| `RequestReconcile()` | Declarations or configured values may change | Rebuild affected subtree, then layout and render. |
| `RequestLayout()` | Bounds, clipping, scrolling, or input regions may change | Arrange roots, rebuild regions, and render. |
| `RequestRender()` | Only visual state changed | Paint from cached bounds without rebuilding regions. |

`DialogRenderer` advances the focused node, drains scoped rebuilds, checks GUI scale
and dialog size, performs the strongest pending invalidation, blits the main texture,
then renders overlay and tooltip layers. Cairo component coordinates are logical
pixels; the surface context applies `RuntimeEnv.GUIScale`.

## Input model

- Mouse and resize routing use regions recorded from positioned layout results.
  Reverse-order hit testing gives later-rendered regions priority, and mouse-down
  capture keeps release behavior tied to the pressed region.
- Keyboard routing is focus-based. Root-dialog handlers run before handlers for the
  node tracked by `FocusManager`.
- Mouse-down without a focus request blurs the focused node. Escape first blurs an
  active node; a later Escape with no focused node requests dialog close.
- Tooltips are visual-only floating content. Overlay layers may contribute interactive
  regions outside the main dialog surface.
