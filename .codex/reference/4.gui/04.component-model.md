# Component Model

The framework separates tree participation, arrangement, resizing, and dialog behavior into small contracts. Interfaces define node capabilities, while `GuiSlot` is the framework-owned mounted runtime contract. The provided component base classes supply convenient default behavior but are never required.

## Public Contracts

| Contract | Responsibility |
| --- | --- |
| `IGuiNode` | Render fragment, attachment, lifecycle, frame updates, and drawing hooks |
| `IGuiComponent` | Adds layout participation through `LayoutParameters` and parameterless `Arrange()` |
| `IGuiResizable` | Extends a component with supported resize edges and framework-suggested bounds |
| `IGuiDialog` | Adds screen-centred offsets and optional dialog-runtime attachment to a component |
| `GuiSlot` | Exposes a node's framework-owned mounted position, tree relationships, cached bounds, arrangement state, and runtime requests |

`GuiNode` is the base for layout-transparent wrappers. `GuiComponent` supplies default stack-like arrangement. `GuiDialog` adds normal dialog runtime, focus, close, movement, and resizing behavior.

## Node Lifecycle

`IGuiNode` provides:

- `TreeFragment`
- `Attach(slot)`
- `OnInitialized()`
- `OnParametersSet()`
- `OnFrame(deltaTime)`
- `Render(context, bounds)`
- `RenderOverlay(context, bounds)`

Attachment happens once after construction. The attached `GuiSlot` exposes the node's structural `Parent`, `Children`, arrangement result, and arrangement operation, making the mounted tree navigable and usable by direct interface implementations; root-level slots have no parent. Initialization happens on first mount. Parameters are applied on every reconciliation pass. `OnFrame` runs once per GUI frame while the node is focused. `RenderOverlay` runs after the node's children but before later siblings.

The reconciliation order and keyed identity rules are documented in [Reconciliation](02.reconciliation.md).

## Configuration Lifecycle

Render-tree declarations describe the full state for the current pass, not a delta from the previous pass.

For a reused slot, the framework:

1. Clears configuration and callback actions from the previous pass.
2. Resets layout parameters to framework defaults for layout components.
3. Applies the node's own `ConfigureSlot` defaults and callbacks.
4. Applies external `Configure`, `ConfigureLayout`, inline layout arguments, and callbacks.
5. Runs lifecycle methods and reconciles children.

Re-register configuration on every `BuildComponentTree` pass. External layout configuration overrides component defaults. Own-slot and external event callbacks are additive, with own-slot callbacks running first.

Use `ConfigureSlot(IGuiSlotBuilder)` for defaults and events attached to a component's own bounds. Use external builder configuration for values owned by the parent declaration.

## Declaring Components

Public authoring goes through extension methods:

- `Add<T>(key, ...)` declares any `IGuiNode`.
- `AddContainer`, `AddLabel`, and other `Add*` helpers provide common component declarations.
- `.Configure(Action<T>)` applies component state.
- `.ConfigureLayout(...)` applies layout state to `IGuiComponent` slots.
- `.OnMouse*`, `.OnKey*`, and `.OnFocusChanged` attach slot callbacks.
- `AddCascadingValue<T>` publishes an ambient value to a declared subtree.

Layout arguments apply only to `IGuiComponent` slots. A pure `IGuiNode` is layout-transparent, so configure layout on its children instead. See [Layout parameters](05.layout-parameters.md).

The low-level builder registration methods are internal. Add new public authoring helpers as extension methods rather than exposing builder internals.

## Arrangement

Sizing and positioning are one component-owned operation:

```csharp
public interface IGuiComponent : IGuiNode
{
    GuiComponentLayoutParameters LayoutParameters { get; }

    GuiComponentBounds Arrange();
}
```

`IGuiComponent.Arrange()` takes no arguments and always returns a `GuiComponentBounds` value. During the transition, slot-level arrangement may still expose nullable cached results. A component reads its mounted slot to inspect its parent, siblings, descendants, and previously calculated arrangement results. The framework initiates arrangement at tree roots; each component owns descendant traversal and chooses when and in what dependency order to call descendant slots.

```csharp
public abstract class GuiSlot
{
    GuiSlot? Parent { get; }
    IReadOnlyList<GuiSlot> Children { get; }

    GuiComponentBounds? Bounds { get; }
    bool IsArranging { get; }

    void Arrange();
}
```

Component-owned traversal supports both normal flow and dependency-sensitive layouts. A stack can arrange descendants in flow order, while a table can inspect and recalculate cells across multiple rows before finalizing shared tracks.

Each component-slot `Arrange()` call invokes the mounted component and caches its returned bounds. Callers read the result from `Bounds`; reading it does not initiate arrangement. Repeated sequential calls re-evaluate dependencies, `IsArranging` reports current execution state, and recursive entry into the same component slot is rejected.

Arrangement state has four meaningful levels during the transition:

1. Slot-level `Bounds == null` — no cached arrangement result is currently available.
2. Non-null with `Bounds.Size == null` — arranged size cannot yet be resolved.
3. Non-null with `Bounds.Size != null && Bounds.Position == null` — size is resolved, but position is not.
4. Non-null with `Bounds.Size != null && Bounds.Position != null` — size and position are resolved.

A component returns bounds with `Size == null` when arrangement ran but size still depends on unresolved inputs such as a parent percentage, remaining flow space, wrapped-text width, or shared table tracks.

`GuiComponentBounds` is deliberately minimal:

```csharp
public readonly record struct GuiComponentBounds(
    GuiPoint? Position,
    GuiLayoutSize? Size);
```

`Position` is the top-left reference point. Logical X increases rightward and logical Y increases downward. Keeping position and size independently nullable lets components expose whichever parts of arrangement are known without inventing missing geometry.

Pure `IGuiNode` wrappers remain layout-transparent and do not implement component `Arrange()` themselves. Slot/framework pass-through handling arranges their descendants without introducing a layout box.

`GuiComponent` provides default arrangement behavior, but direct `IGuiComponent` implementations have the same capabilities through their attached slot and do not need to inherit from it.

## Choosing an Invalidation Request

| Change | Request |
| --- | --- |
| Child declarations or configured values depend on changed state | `RequestReconcile()` |
| Cached arrangement results, clipping, scrolling, or input regions may be stale | `RequestLayout()` |
| Existing arrangement results are valid and only visuals changed | `RequestRender()` |

Base-derived and direct interface implementations issue reconciliation, layout, and render requests through their attached `GuiSlot`.

## Cascading Values

`AddCascadingValue<T>(value, content, name?)` creates a lexical scope without adding a component or layout slot.

Consumers use `GetCascadingValue<T>` or `TryGetCascadingValue<T>` from `GuiNode`; direct implementations use `GuiSlot.TryGetCascadingValue<T>`.

Resolution uses the exact type and optional name. The nearest matching scope wins, and an unnamed lookup matches only an unnamed provider. Read cascading values during `OnParametersSet` when the component needs a per-pass snapshot.

## Dialog Components

`IGuiDialog` extends `IGuiComponent` with `OffsetX`, `OffsetY`, and optional runtime attachment. Hosts and renderers accept any `class, IGuiDialog, new()`.

Use `GuiDialog` for normal dialogs. It provides:

- Runtime attachment and protected close/focus helpers.
- Native dialog focus tracking.
- Screen-centred offsets and movement.
- Optional resizing through `IGuiResizable`.

Set default dialog dimensions in `ConfigureSlot` so reconciliation can reset and reapply them. Register dialog-wide keyboard and focus behavior on the root slot. Implement `IDisposable` only when a dialog or child node owns resources; slot removal disposes nodes that opt in.

Dialogs do not own an `Open`, `Close`, or `IsOpen` state. They request closure, and the host owns their lifetime.
